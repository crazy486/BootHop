# Minimal Arch direct boot for BootHop

Date: 2026-10-02. Status: design for the isolated `codex/arch-uki-minimal` branch. This document authorizes code and fake or isolated tests only; it does not authorize host ESP, efivarfs, mkinitcpio preset, GRUB, BootNext, or reboot operations.

## Product contract

Normal power-on still follows the existing `Boot0000 → GRUB menu` path. A one-time Windows BootHop switch selects a dedicated `BootHop Arch` entry pointing to `\EFI\BootHop\arch.efi`; firmware consumes `BootNext` and the next normal power-on returns to the original GRUB menu. The already verified Windows → original GRUB → manual Arch choice remains available. Daily Switch writes only `BootNext` and does not create entries or read the UKI from Windows.

## Scope and trust boundary

This is for one fixed Arch Linux + Windows 11 UEFI installation. Linux explicit setup is a separate, root-only, user-invoked operation, never a side effect of Inspect, Configure, or Switch. It accepts a validated installed kernel preset name, but no caller-supplied ESP path, Boot ID, EFI bytes, device identity, or BootOrder. The existing Windows protected target record, canonical identity validation, BootNext conflict/readback, and reboot flow remain authoritative. The existing `Boot0000`, its GRUB files, and Windows Boot Manager must never be overwritten or reordered.

## Explicit Linux setup

1. Read and report the chosen installed kernel flavor, a persistent `/etc/kernel/cmdline` source, exact mounted ESP and GPT partition, current Secure Boot state, current BootOrder, BootNext, and candidate `Boot####` namespace. Ambiguous kernel choice, dynamic or absent cmdline, unsupported ESP layout, unknown firmware state, or any existing BootNext stops before mutation. Secure Boot enabled stops this MVP until a separately reviewed signing and trust path exists.
2. Add one `boothop` stanza to the selected existing `/etc/mkinitcpio.d/<flavor>.preset`, preserving its other presets: `boothop_uki` names a staging file beside the fixed `EFI/BootHop/arch.efi`, and `boothop_cmdline=/etc/kernel/cmdline`. A single installed mkinitcpio post hook acts only on that exact staged output; it validates the completed UKI and atomically renames it to the fixed path on the same ESP. It rejects symlinked ESP parents/stage/final paths and requires a freshly generated stage, never accepting residue from an earlier failed build. The explicit initial setup invocation supplies a root-only initial-mode flag and requires the final path and installation marker to be absent. Later package updates use the same hook only after parsing a root-owned marker with supported schema, exact fixed path, valid Boot ID syntax, and valid saved load-option digest encoding, and confirming the final path is a non-symlink regular file. The hook does not re-read firmware; Windows Switch checks the live Boot#### identity. A corrupt, foreign, or unsupported marker blocks publication. Neither mode advances transaction checkpoints. A failed build or validation leaves the previous fixed image intact. Before Boot#### mutation, setup must verify the host package update script rebuilds the selected existing preset and does not suppress post hooks, then run that preset and verify the published image. Unsupported preset syntax or update routing stops.
3. Construct exactly one active EFI load option with a GPT `HD()` node, fixed `File()` path, `BootHop Arch` description, and empty OptionalData. Scan all Boot-like variables, including orphan `Boot####`, choose an unused ID, create exclusively once, and read back the exact bytes. A collision or unknown result stops; it never overwrites, retries, allocates another ID, or deletes an entry.
4. Re-check BootNext absence and the exact newly created Boot#### immediately before appending. Re-read the latest valid BootOrder. Append only the new ID at the tail while preserving every prior ID and its relative order. Write once and read back the entire expected order. A mismatch or uncertain write stops without a rollback attempt. `Boot0000` must remain first; otherwise setup refuses to append. External firmware writers can still race between read and write because BootOrder has no compare-and-swap; this procedure does not claim transaction safety.
5. After successful readback, atomically save one root-owned installation identity file: schema version, Boot ID, exact load-option digest/identity, and fixed artifact path. This is an installed marker, not a transaction journal. Missing or corrupt markers and any pre-existing matching artifact/entry cause a new setup to stop for manual inspection, not to infer ownership.

There is no automatic retry, rollback, reconciliation, recovery, or uninstall. An interrupted setup may leave an orphan entry or a trailing BootOrder item. The original GRUB path remains the recovery path.

## Update and maintenance

The selected kernel's normal mkinitcpio update path must rebuild the same fixed UKI through that one staging/validation/rename hook. The host's kernel package hook currently invokes the selected preset by package base; setup verifies this live rather than relying on that observation forever. A kernel-install path that suppresses post hooks is unsupported. No daemon, versioned BootHop kernel copy, or journal hash handshake is added. The publisher may update only the fixed BootHop path; failure keeps the previous file and reports an error. A failed kernel-package update can leave the old UKI whose matching modules have since been removed; that image may be unbootable despite atomic publication. After any such failure, the user must rebuild and re-accept the direct path before relying on Windows Switch; Windows cannot detect it. A kernel or command-line change can also make a syntactically valid UKI unbootable, so isolated boot acceptance is required. Manual uninstall is documented as read-only inspection followed by administrator-controlled cleanup of precisely identified objects; the MVP has no automatic uninstall code or UI.

## Daily Windows Switch

The user explicitly configures the discovered dedicated entry once through existing Inspect/Configure. On every Switch, the Windows helper reloads the protected target, compares the live Boot ID and canonical identity (including fixed path and exact OptionalData), checks BootNext conflict state, writes only BootNext when absent, reads it back, then requests a normal reboot. It does not open the ESP or inspect the UKI file. Missing/changed entry, unknown BootNext, or failed readback stops. A UKI failure may require selecting the original GRUB entry from firmware; neither identity validation nor PE-format checks prove the image will boot.

## Failure report and acceptance

On setup failure, stop mutations, perform only safe read-only inspection, and report the BootHop preset stanza and post-hook installation/exactness, artifact existence, selected Boot ID and exact entry match, current BootOrder membership/order, BootNext, and which observations are unknown. An interruption after preset/hook installation but before the identity marker can make later mkinitcpio runs fail closed; the manual guide must cover that partial configuration as well as firmware objects. Do not equate absence or presence with proof of successful mutation. The guide must explain verification before any `efibootmgr` cleanup and forbid deleting by label alone.

Fake tests cover occupied and orphan IDs, exclusive-create collisions, exact readback mismatch, malformed BootOrder, tail-only append, old-order preservation, uncertain writes without retry, and partial failure reporting. Isolated UEFI acceptance must demonstrate normal GRUB boot, BootNext direct Arch boot and consumption, return to GRUB on the next ordinary boot, update boot, and interruption without damage to original Boot0000. CI and fakes never access host firmware or reboot.

## Option D gate: NO-GO

A separate no-menu GRUB EFI could reuse the existing stable kernel/initramfs filenames on this ESP. It still requires a second GRUB image and boot configuration, separately maintained kernel command line and initrd order, GRUB update compatibility, signing policy if Secure Boot changes, and separate boot tests. That is not a clear reduction in setup, maintenance, and test cost versus the fixed UKI. The Go bar in this review therefore rejects Option D; no implementation branch is opened for it. References: [GRUB embedded configuration](https://www.gnu.org/software/grub/manual/grub/html_node/Embedded-configuration.html), [GRUB Linux boot sequence](https://www.gnu.org/software/grub/manual/grub/html_node/GNU_002fLinux.html), [mkinitcpio presets](https://man.archlinux.org/man/mkinitcpio.8.html).

## Deliberate exclusions

No persistent transaction journal, lifecycle checkpoint enum, residual graph, proof-bound commits, automatic reconciliation/recovery/uninstall, Windows EFI-volume reader, per-Switch UKI file check, expanded GUI PE file-write provenance gate, or lifecycle status UI. These mechanisms are not copied from `codex/arch-uki-direct-boot` merely because they already exist.
